# Rust vs Python end-to-end performance evaluation

This benchmark evaluates **PacketHawk (Rust)** and **ArgusProwl (Python)** on the
same six raw captures from the public CTU-IDSEVAL-6 dataset
([DOI 10.5281/zenodo.21027042](https://doi.org/10.5281/zenodo.21027042),
CC-BY-4.0). Both repository revisions, the dataset archive checksums, Python,
Rust, Zeek, runner hardware, and per-capture PCAP SHA-256 are written into the
JSON report.

## Do not misread this as an equivalent detector shootout

The products do different work:

- PacketHawk consumes raw PCAP packets, decodes supported network metadata,
  and runs its packet/flow detections.
- ArgusProwl consumes Zeek-normalized connection records, parses them into
  normalized events, runs its production application event path, and persists
  resulting alerts.

There is no semantic parity claim between their detection rules or alert
counts. Zeek conversion is measured separately and included in the
ArgusProwl end-to-end wall-time total. ArgusProwl's labeled CTU precision,
recall, F1, and false-positive rate are included as efficacy metrics; they are
not directly compared to PacketHawk's heuristic findings.

## Measurements

For every real capture and repeat:

- Input bytes and SHA-256.
- Zeek conversion wall time and generated conn.log size.
- PacketHawk raw-PCAP detection and flow aggregation wall time, CPU user/system
  time, peak RSS, packet count, flow count, state evictions, flow evictions,
  and individual detector alert counters.
- ArgusProwl application startup time, event-processing time, worker wall
  time, CPU user/system time, peak RSS, parsed flow count, persisted alerts,
  and CTU ground-truth metrics.
- Five cold process/import startup probes for both executables/runtimes.

The harness runs each Python evaluation in a fresh worker with a fresh SQLite
state directory. Rust commands are also separate processes. This avoids
cross-capture state contamination. The JSON report retains every repeat rather
than hiding variance behind a single average.

## Saturation and parser boundaries

A second, explicitly **derived stress fixture** is generated by mutating the
IPv4 addresses and transport ports of a real packet frame. It is not presented
as a real capture or used for efficacy claims. Its 262,144 packet default is
designed to exceed PacketHawk's 100,000-flow table capacity and exercise its
bounded scan/beacon state eviction counters. A parallel 262,144-event Zeek
fixture, derived from a real generated Zeek row with unique UIDs and timestamps,
drives the ArgusProwl production application event path and durable alert
persistence. These are capacity tests, not representative benign/malicious
traffic distributions.

PacketHawk fail-fast boundary probes cover:
- Capture file size above 512 MiB.
- A packet record above 16 MiB.
- A PCAPNG block above its configured block-size limit.

The probes use sparse/truncated headers so they can verify rejection without
allocating the claimed payload sizes. Flow/state eviction counts must be
non-zero in the saturation case or the benchmark fails.

## Reproduction

The GitHub Actions workflow checks out PacketHawk at the immutable commit
recorded in the report, builds its release binary, installs the locked
ArgusProwl environment, downloads and checksum-validates the CTU archives,
runs Zeek in a network-isolated container, and publishes the JSON report as a
90-day artifact.

Run locally after building PacketHawk:

\`\`\`bash
uv sync --frozen
cargo build --locked --release --manifest-path ../PacketHawk/Cargo.toml

uv run python scripts/evaluation/rust_python_pcap_benchmark.py \\
  --workspace .tmp/rust-python-benchmark \\
  --output .tmp/rust-python-benchmark/report.json \\
  --packethawk-bin ../PacketHawk/target/release/packethawk \\
  --repeats 3 \\
  --stress-packets 262144
\`\`\`

The runner needs Docker for the pinned Zeek image, network access to Zenodo for
the first dataset download, and enough free disk space for the archives,
extracted captures, generated Zeek logs, SQLite state, and reports.

## Decision rule for Rust adoption

Do not port code because Rust wins a parser microbenchmark. Consider a Rust
component only when repeated, same-runner measurements show a material
end-to-end bottleneck in a Python hot path and a prototype preserves detection
semantics, evidence, ordering, failure behavior, and bounded-state guarantees.

A practical decision gate is:
1. Identify the measured stage dominating CPU or wall time.
2. Profile that stage before rewriting it.
3. Prototype only that isolated hot path in Rust.
4. Compare end-to-end throughput, p95 latency, peak RSS, startup cost,
   operational complexity, and correctness on the same captures.
5. Keep the Python implementation unless the Rust component delivers a
   sustained improvement large enough to justify FFI/build/deployment cost.

Hosted GitHub runners are suitable for repeatable regression evidence, not
absolute hardware-independent performance claims. Re-run on the intended
deployment hardware before selecting a production architecture.
